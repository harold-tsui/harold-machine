# harold-machine

> Harold Finch 造了一台会自己判断的机器。这台是我的——它只判断什么值得交付。

18 个技能 + 1 个入口，覆盖一个人的内容生意从研究、决策、生产到运营的完整链路。每个技能都写明**阻塞项、计分项和一条可复算的判定行**：不达标就重写，不靠"感觉还行"。

## 它解决什么问题

普通提示词合集的问题是：用完之后没人知道这次到底算不算做完。这里把"做完"写成可复算的条件。

一个技能不是一段好用的提示词，而是四件东西的组合：

| 组成 | 作用 |
|---|---|
| 触发说法 | 什么请求该用它，什么请求不该用 |
| 工作流 | 分几步、每步要什么输入、缺输入怎么办 |
| 输出格式 | 交付物长什么样，字段不可省略 |
| 验收标准 | 阻塞项 + 计分项 + 判定行，能算出通过或不通过 |

同一套验收口径由 `harold-gov-gate` 维护，全库只有一条：

> 阻塞全过 + 计分 ≥ ⌈0.8 × N⌉ = 可交付；计分 ≤ 阈值-1 = 重写；阻塞任一为 0 = 重做

换算固定：5 项 → 4；6 项 → 5；7 项 → 6；9 项 → 8；12 项 → 10。其他技能只能引用，不能自造阈值。

## 五层结构

| 层 | 回答什么 | 技能数 |
|---|---|---|
| L0 治理 `01-governance` | 谁能进库、怎么验收 | 1 |
| L1 决策 `02-decision` | 该不该做、怎么取舍 | 2 |
| L2 研究 `03-research` | 把不确定变成可引用结论 | 2 |
| L3 生产 `04-production` | 把结论变成可交付物 | 8 |
| L4 运营 `05-operations` | 让事情闭环、知识留痕 | 5 |

外加入口技能 `using-harold-machine`：每轮先分诊出唯一主技能，再动手；没有合适的就直接做，不硬套。

研究负责"是什么"，决策负责"做不做"，生产负责"怎么交付"，运营负责"有没有落地"。四者不互相替代；缺证据时决策只能给暂缓。

## 适合谁

- 你已经在持续产出内容（长文、公众号、小红书、PPT、网页），想要一条可验收的流水线。
- 你愿意为每个交付物补上口径、来源和验收记录，而不是要一段"写得更像人"的提示词。
- 你能接受技能判断与你不同，并按它的流程返工。

不适合：想要开箱即用的万能助手；只写一次性短文；不接受任何格式约束。

## 现在开始

```bash
git clone https://github.com/harold-tsui/harold-machine.git
```

1. 先读 [USAGE.md](USAGE.md)，看一轮任务怎么走完。
2. 按 [INSTALL.md](INSTALL.md) 把需要的技能链接进客户端。
3. 第一轮只装入口加一两个最常用的技能，跑通再扩。

## 一个技能长什么样

```text
<层目录>/<slug>/
├── SKILL.md        # 唯一入口，≤300 行
├── references/     # 按需加载，最多一层
├── scripts/        # 只有脆弱操作才写
├── assets/         # 模板
└── evals/          # 验收用例：输入 → 期望特征
```

文件夹名就是技能名（slug），格式 `harold-<层>-<职能>`，全小写 ASCII。`SKILL.md` 末尾的验收标准与 `evals/cases.md` 的评分表条数、顺序、语义一一对应。

## 为什么叫 harold-machine

- `harold` 是作者的名字，也是《疑犯追踪》里造机器的人的名字。
- 那台机器的流程是「输入 → 判定 relevant / irrelevant → 派人执行 → 自我纠偏」，和这里的 L0 → L4 是同一条链。
